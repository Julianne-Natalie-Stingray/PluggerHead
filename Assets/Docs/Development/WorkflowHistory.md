# 1    工作流总述 / Workflow Overview

## 1.1    分工 / Division of labour

- DSH用于简化编程工序, 但不接管Inspector操作和资产, 场景, 预制体编辑
- DSH simplifies the programming process only. It does not take over Inspector operations, or asset, scene, and prefab editing.
- 对副本进行改动后, 我审批并修改, merge到主分支. 
- After changes are made to the clone, I review and amend them, then merge to the main branch.
- 如果我的指令与该文件产生冲突, 停止并询问
- If my instruction conflicts with this file, stop and ask.

## 1.2    写入边界 / Write boundary

- DSH写权限仅限 `workspace-write`, 即本工作区之内. 如果不慎改变应立刻停止并询问. 
- DSH's write permission is `workspace-write` only, i.e. inside this workspace. If it is ever changed by accident, stop immediately and ask.
- 工作区内只有一条写入路径: `Assets/`. 其余位置一律禁止写入, 除非本节或 §2.2 明确许可. 
- Inside the workspace there is exactly one write path: `Assets/`. Every other location is off limits unless this section or §2.2 explicitly permits it.

## 1.3    读取边界 / Read boundary

- **读取权限无边界. 沙箱只限制写入, 不限制读取.**
- **Read permission is unbounded. The sandbox constrains writes only, never reads.**
- 工程本体位于本工作区之外, 与副本共享同一个 `.git`. DSH能够读到本体及其 git 元数据, 这是已知且已被接受的事实, 不是"DSH对本体一无所知". 
- The main project lives outside this workspace and shares the same `.git` as the clone. DSH can read the main project and its git metadata. This is a known and accepted fact, not a claim that "DSH is ignorant of the main project".
- 因此, 下述行为是本工作流**唯一**的隔离手段: DSH不得主动访问本工作区之外的任何路径, 不得读取工程本体, 不得读取本体的 `.git`. 该约束由纪律承载, 不由机制承载. 
- Therefore the following is the **only** isolation this workflow has: DSH must not proactively access any path outside this workspace, must not read the main project, and must not read the main project's `.git`. This constraint is carried by discipline, not by a mechanism.
- 当某项操作看起来必须越界时, 停止并询问, 由我代为执行. 
- When an operation appears to require crossing that boundary, stop and ask, and I will perform it instead.

## 1.4    单一写入路径 / Single write path

- 所有改动都发生在 `Assets/` 之下. `ProjectSettings/`,  `Packages/` 属于 §2.2 的例外情形, 需先申请. 
- All changes happen under `Assets/`. `ProjectSettings/` and `Packages/` are the exceptions governed by §2.2 and require a prior request.
- 我负责的部分是Core / Environment, 只允许动`Jill/`目录下的文件.

# 2    写入权限 / Write Permissions

## 2.1    文件类型 / File types

- 可以写入 / Writable: `.cs`, `.asmdef`, `.json`, `.md`
- 禁止写入 / Forbidden: `.git`, `.vs`, `.meta`, `.idea`, `.unity`, `.scene`, `.prefab`, `.asset`

### 2.1.1    `.meta` 规则 / The `.meta` rule

- DSH不得创建, 删除或编辑任何 `.meta` 文件. GUID只能由Unity生成. 
- DSH must not create, delete, or edit any `.meta` file. GUIDs are generated by Unity alone.
- DSH新增或改名文件后, 对应的 `.meta` 处于"等待Unity生成"状态. DSH不得代为编造GUID. 
- After DSH adds or renames a file, the matching `.meta` is in a "waiting for Unity" state. DSH must not fabricate a GUID on its behalf.
- 该 `.meta` 必须与它的文件**一起提交**. GUID一经生成即不可重建: 若 `.meta` 丢失, Unity会为新文件分配**不同的GUID**, 已引用该脚本的场景与预制体会变成"unassigned script". 
- That `.meta` must be committed **together with** its file. A generated GUID cannot be recreated: if the `.meta` is lost, Unity assigns a **different GUID**, and scenes and prefabs referencing that script become "unassigned script" components.
- 孤儿 `.meta` 由Unity删除, 不由DSH删除. 
- Orphan `.meta` files are deleted by Unity, never by DSH.
- 因此: 每次交付必须在 `Assets/CHANGELOG.md` 中列出本次新增的 `.cs` 文件及其**待Unity生成的 `.meta`** 清单, 供我核对提交. 
- Consequently: every delivery must list, in `Assets/CHANGELOG.md`, the `.cs` files added by that delivery together with their **pending `.meta`** files, so that I can verify and commit them.

# 3    操作权限 / Operation Permissions

## 3.1    允许的操作 / Permitted operations

- 创建 / 修改部分 `.cs`, `.asmdef`, `.json`, `.md`
- Create and modify the permitted `.cs`, `.asmdef`, `.json`, and `.md` files.
- 申请后可改动 `ProjectSettings/`
- `ProjectSettings/` becomes writable after a request is granted.
- 申请后可以修改 `Editor` 脚本
- `Editor` scripts become modifiable after a request is granted.
- 只读的git操作 / Read-only git operations: `status`, `diff`, `log`, `show`
- `git update-index --refresh` —— 允许, 且**仅此一条** `update-index` 形式. 它只刷新索引中记录的文件状态缓存, 不改变任何被跟踪文件的内容, 不动 `HEAD`, 不动工作区. 禁止 `--add`, `--remove`, `--force-remove` 以及任何其他 `update-index` 形式. 
- `git update-index --refresh` is permitted, and it is the **only** permitted form of `update-index`. It only refreshes the stat cache recorded in the index; it changes no tracked file's content, does not move `HEAD`, and does not touch the working tree. `--add`, `--remove`, `--force-remove`, and every other form of `update-index` are forbidden.
- 允许该命令的理由 / Why it is permitted: 整个审批流程建立在"`git status` 不说谎"之上. 幽灵 ` M` 标记会训练我忽略这个标记, 而它正是唯一能看见越界写入的像素. 
- The whole approval flow rests on `git status` not lying. A phantom ` M` marker trains me to ignore that marker, which is the only pixel through which an out-of-bounds write becomes visible.

  - 注意: Unity自身会在导入时重写这些文件 (例如修正过期的源路径注释). 由此产生的 diff 是**预期的**, 不属于DSH的越界写入. 
  - Note: Unity itself rewrites these files on import (for example, correcting a stale source-path comment). A diff arising from that rewrite is **expected** and is not an out-of-bounds write by DSH.
- 任何涉及 `Inspector` 的操作
- Any operation that touches the `Inspector`.
- 任何对场景, 预制体的操作
- Any operation on scenes or prefabs.
- `git commit`, `push`, `merge`, `rebase`, `reset`, `checkout`, `switch`, `clean`, `add`
- `git commit`, `push`, `merge`, `rebase`, `reset`, `checkout`, `switch`, `clean`, `add`.

## 3.3    会话前置条件 / Session preconditions

- DSH在本工作区开工之前, **必须**确认副本正被一个Unity GUI实例打开. 判定依据: `Temp/UnityLockfile` 存在, 且没有陈旧的 Unity Editor 进程残留. 
- Before starting any work in this workspace, DSH **must** confirm that the clone is currently open in a Unity GUI instance. The test is: `Temp/UnityLockfile` exists, and no stale Unity Editor process is holding the project.
- 之所以强制: DSH禁止写入 `.meta`, 而Unity只在导入资产时生成 `.meta`. 若Unity未打开副本, DSH新建的 `.cs` 将永久停留在"无 `.meta`"的不可导入状态, 且没有任何机制会去补它. 
- Why this is mandatory: DSH is forbidden from writing `.meta`, and Unity generates `.meta` only while importing assets. If Unity is not holding the clone, a newly created `.cs` stays unimportable with no `.meta`, and nothing else will ever supply one.
- 若该前提不成立: **立即停止并询问**, 不得开始任何写入. 
- If the precondition does not hold: **stop immediately and ask**, and begin no writes.
- 同一工程目录不允许被两个Unity进程同时打开 (Unity自身会拒绝). 因此DSH不得对副本启动任何第二Unity实例或命令行Unity进程. 
- A single project directory must not be opened by two Unity processes at once (Unity refuses this itself). DSH therefore must not start a second Unity instance or any command-line Unity process against the clone.
- 我的操作时序承诺: 我会在DSH完整交付一份工作之后才操作GUI. 因此DSH不应预期在交付中途得到Inspector反馈. 
- My side of the timing contract: I operate the GUI only after DSH has delivered one complete unit of work. DSH should therefore not expect Inspector feedback mid-delivery.

# 4    交付粒度 / Delivery Granularity

## 4.1    交付单元 / Unit of delivery

- 一份交付的单位是**一个Subsystem**, 不是单个文件, 也不是整个工程. 
- One unit of delivery is **one Subsystem** — not a single file, and not the whole project.
- 一份交付应包含: 该Subsystem的全部脚本改动, 该Subsystem的 `README.md`, 以及 `Assets/CHANGELOG.md` 与 `Assets/PENDING_INSPECTOR.md` 的增量. 
- One delivery contains: all script changes for that Subsystem, that Subsystem's `README.md`, and the increments to `Assets/CHANGELOG.md` and `Assets/PENDING_INSPECTOR.md`.
- **"完整"指编译意义上的完整, 不指设计意义上的完整.** 交付边界处代码必须能编译. 设计仍可迭代, 交付之后继续对同一Subsystem迭代是允许且预期的. 
- **"Complete" means complete in the compilation sense, not in the design sense.** The code must compile at the delivery boundary. The design may still iterate; continuing to iterate on the same Subsystem after a delivery is allowed and expected.

## 4.2    跨Subsystem接口 / Cross-Subsystem interfaces

- 若一份交付需要引用另一个Subsystem尚未交付的接口, 该接口属于**设计上的不完整**, 会使编译边界不成立. 
- If a delivery needs an interface from another Subsystem that has not been delivered yet, that interface is a **design-level incompleteness** and breaks the compilation boundary.
- 此时**先问再写**: 停止, 说明所缺接口, 等我裁决. 不得先写半个接口. 
- In that case **ask before writing**: stop, name the missing interface, and wait for my decision. Never write half an interface first.
- 该规则同时满足 §5.2.1 "Subsystem间低耦合": 跨Subsystem的引用点应当少而显式. 
- This rule also serves §5.2.1 "low coupling between Subsystems": cross-Subsystem reference points should be few and explicit.

## 5.2    代码规范 / Code standards

### 5.2.1    基本原则 / Principles

- Subsystem内高内聚, Subsystem间低耦合
- High cohesion inside a Subsystem, low coupling between Subsystems.
- 组合大于继承, 避免使用简单class继承, 尽量少用abstract class继承, 但interface继承不在此列
- Prefer composition over inheritance; avoid plain class inheritance, use abstract class inheritance sparingly, but interface inheritance is exempt from this.
- 谨慎做interface抽象, 除非有 ≥3 个类型拥有相同特性, 或者需要划清ownership / scope
- Abstract an interface only with care, unless ≥3 types share the trait, or ownership or scope must be drawn explicitly.
- 尽可能避免magic string match
- Avoid magic string matching wherever possible.
- 少用单例范式
- Use the Singleton pattern sparingly.
- 最小化暴露字段 / 方法, 公共字段除非确有写入需要, 全部使用Property + backing field暴露
- Minimise exposed fields and methods; unless a field genuinely must be written from outside, expose it as a Property with a backing field.
- 不使用序列化字段 + Inspector赋值解决引用, 尽量通过 `GetComponent<>()` + 缓存解决依赖, 除非依赖与场景高度相关必须手动赋值, 或确有需要
- Do not resolve references through serialized fields plus Inspector assignment. Resolve dependencies through `GetComponent<>()` plus caching, unless the dependency is so scene-specific that it must be assigned by hand, or there is a genuine need.
- 数据持久化优于直接序列化, 多使用ScriptableObject
- Prefer data persistence over direct serialization; use ScriptableObjects liberally.
- 相互耦合的多个脚本共用同一份数据时, 使用property映射, 减少inspector赋值操作
- When several coupled scripts share one body of data, map it through properties to reduce Inspector assignment work.

### 5.2.2    代码模版 / Code template

#### 5.2.2.1    Region / If 分区 / Regions and conditional sections

- 暴露的Properties超过5个, 划入 `APIs` 区域
- More than five exposed Properties go into an `APIs` region.
- `OnValidate()` 等划入 `if UNITY_EDITOR`, 放在代码最后
- `OnValidate()` and the like go into `if UNITY_EDITOR`, at the very end of the file.
- 测试用方法划入 `Debug` 区域, 放在代码最后 (与 `if UNITY_EDITOR` 分区的先后则无关紧要)
- Test-only methods go into a `Debug` region, at the end of the file (their order relative to the `if UNITY_EDITOR` section does not matter).

#### 5.2.2.2    代码排版 / Layout

- 一个 `.cs` 文件内只能有一个class / enum / struct / etc.
- One `.cs` file holds exactly one class, enum, struct, or similar.
- XML注解先于 Attributes
- XML documentation precedes Attributes.
- 代码块间空一行, 代码块内不空行
- One blank line between code blocks, no blank lines inside a block.
- 每个方法占一个代码块, 方法内根据代码逻辑分块
- Each method is one code block; inside a method, split by logic.
- 公共Properties占一个代码块(并可能划分region), 放在最前
- Public Properties form one block (possibly split into regions), placed first.
- 序列化私有字段占一个代码块, 放在第二块
- Serialized private fields form one block, placed second.
- 运行时变量不序列化, 占一个代码块, 放在第三块
- Non-serialized runtime variables form one block, placed third.
- 常量占一个代码块, 放在第四块
- Constants form one block, placed fourth.
- Debug相关字段和Debug方法一起放在Debug分区内
- Debug-only fields and Debug-only methods live together in the `Debug` region.
- Unity生命周期方法相邻, 放在方法最前面
- Unity lifecycle methods are adjacent and come first among methods.
- 一个方法的多个重载相邻
- Overloads of one method are adjacent.
- 工具方法, Gizmos方法和 `InitializeInternal` / `ResolveDependencies` 方法放在除 `Debug` 之外的方法后
- Utility methods, Gizmos methods, and `InitializeInternal` / `ResolveDependencies` go after all methods except those in `Debug`.

#### 5.2.2.3    方法名规范 / Method names

- `InitializeInternal` 方法解决Subsystem内部依赖
- `InitializeInternal` resolves dependencies inside the Subsystem.
- `ResolveDependencies` 方法解决Subsystem间依赖
- `ResolveDependencies` resolves dependencies between Subsystems.
- `Configure` 方法将持久化参数
- `Configure` applies persisted parameters.

#### 5.2.2.4    字段 / 变量名规范 / Field and variable names

- Property: PascalCase
- local variable: camelCase
- private field: camelCase
- constant: camelCase

#### 5.2.2.5    ScriptableObject规范 / ScriptableObject standards

- 命名传统为 `configs`
- The naming convention is `configs`.
- 所有数据全部序列化, 需要暴露的数据创建公共property.
- All data is serialized; data that must be exposed gets a public property.
- 可以提供检索 / 查找等数据相关公有方法, 但不应该包含其他逻辑
- Data-related public methods such as lookup and search are fine, but no other logic belongs there.
- 如有需要, 应支持数据 `Validate`, `Clamp` 和 `Remove Duplicate`
- Where needed, it should support `Validate`, `Clamp`, and `Remove Duplicate` over its data.

#### 5.2.2.6    访问限制词 / Access modifiers

声明时从不省略访问限制词. 
Access modifiers are never omitted from a declaration.

- `public`
- `[SerializeField] private`
- `private`

#### 5.2.2.7    方法调用规范 / Method-call standards

- 初始化使用 `Awake()` 而非 `Start()`
- Initialize in `Awake()`, not `Start()`.
- 持续整个生命周期的订阅使用 `OnEnable()` / `OnDisable()`
- Subscriptions that last the whole lifetime use `OnEnable()` / `OnDisable()`.
- 禁止在高发方法中使用 `GetComponent<>()` / `Find` 和 `System.Linq` 系列方法
- `GetComponent<>()`, `Find`, and the `System.Linq` family are forbidden inside hot methods.

#### 5.2.2.8    Attribute规范 / Attribute standards

- 加入 `using System;`, 使用 `[Serializable]`
- Add `using System;` and use `[Serializable]`.
- 容易产生歧义的序列化字段, 可以添加 `[ToolTip]`
- Ambiguous serialized fields may carry a `[ToolTip]`.
- 详见Unity Package部分 / See the Unity Package section for details.

### 5.2.3    Unity Package

#### 5.2.3.1    NaughtyAttributes

#### 5.2.3.2    MenuTool

- `[CreateAssetMenu]` 属性涉及 `MenuTool` 包, 生成ScriptableObject定义时将其注解掉, 由我修改 `.menutool` 资产后改回. 
- The `[CreateAssetMenu]` attribute involves the `MenuTool` package. When generating a ScriptableObject definition, comment it out; after I amend the `.menutool` asset, restore the attribute.
- 责任划分: DSH注解掉属性, **我**修改 `.menutool` 资产, **我**改回属性. DSH不得写入 `.menutool` 资产, 也不得写入 `Game.MenuTool.g.cs`. 
- Division of responsibility: DSH comments the attribute out, **I** amend the `.menutool` asset, and **I** restore the attribute. DSH must not write the `.menutool` asset, and must not write `Game.MenuTool.g.cs`.
- 该来回构成一次往返, 因此应记入 `Assets/PENDING_INSPECTOR.md`. 
- That round trip counts as a pending item, so it belongs in `Assets/PENDING_INSPECTOR.md`.

#### 5.2.3.3    GameLog
